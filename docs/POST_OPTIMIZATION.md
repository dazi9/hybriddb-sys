# POST-OPTIMIZATION — 优化前后对比（B+树/LSM 两项针对性改进）

**日期**：2026-10-25　**对照基线**：`results_before/`（REPORT.md 的 90 次运行）
**复测**：`results/`（同 op 流、同 seed、同 CPU 60% 限频条件，90 次运行）

## 改动内容（commit `35ede4b`，hybriddb-sys hardening 分支）

1. **CRC32 查表化**：`crc32_ieee` 从逐位循环（4KB 页 33.87 µs）改为 slice-by-8
   表驱动。位级等价（回归测试：501 种长度对照旧实现 + 标准校验值 `0xCBF43926`
   + 链式调用语义），磁盘数据零迁移。
2. **LSM 点查 open-once 句柄缓存**：`search_in_sstable` 此前对每个候选 SSTable
   每次查询都执行 `open()/close()`（`lsm.cpp` 搜索路径）；现在每个 SSTable
   持有缓存的 `DiskManager` 句柄，compaction 退役时关闭。scan 路径同样受益。

## 对照组（未改动的引擎，用于排除环境漂移）

pybitcask 吞吐变化 **0.80x ~ 0.94x**，sqlite-delete **0.83x ~ 0.99x**，
sqlite-wal **0.79x ~ 1.01x**，p50 变化均在 ±6% 内。对照组漂移包络 ±21%，
而两个 C++ 引擎的改善幅度（btree 5.5~10.6x、lsm 1.6~61.5x）远超包络——
提升归因于上述两项改动，而非机器状态差异。

## 归因分析

- **B+树**：before 的读路径 p50（31.1~31.8µs）几乎就是一次缓冲未命中的位级
  CRC32 成本（微基准 33.87µs/页）。查表化后 p50 降到 2.2~2.5µs，与预期一致——
  读密集负载（A/B/C/F）全部 ~10x，扫描 E 7x，D 因走 memtable 追加路径改善较小。
- **LSM**：C（只读）p50 从 108µs → 1.8µs（60 倍），对应消除每查询 3 次
  open/close 的 syscall 链；读类负载（A/B/C/F）改善 16~61 倍。D/E 是写/扫描
  主导，收益小（2.9x / 1.6x）——E 的主要成本在多路归并扫描而非 open。
- **写放大/读放大完全未变**（btree WAF 21.35 before vs 21.35 after，RAF 1.49
  不变）：两项都是纯 CPU 路径优化，不触碰 IO 模式——这正是预期的健全性检查。

## 优化后的全局排名变化

- lsm-B **752,450 ops/s 成为全场第一**（此前 B+树 A 负载 2.5 万垫底）。
- btree-A 264,840 ops/s 追平 sqlite-wal-A（277,271），进入第一梯队。
- lsm-C 446,657 反超 pybitcask-C（332,867）——"C++ 引擎被 Python 引擎碾压"
  的旧结论对读路径不再成立。
- SQLite(WAL) 仍是均衡王（6/6 前二），pybitcask 在 D（写最新）上仍保持优势。
